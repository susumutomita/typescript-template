# Steering Mechanisms（統制機構の使い分け）

steering には継続的なコストがあります。常時ロードされる文章、hook、Skill、subagent は、モデルの能力を補う一方で、古い世代の制約を残し、探索範囲を狭めることがあります。

既定は「追加しない」です。同じ失敗を繰り返し観測し、既存のテスト、型、lint、CI では防げない場合だけ追加します。

## 配置基準

| 機構 | 置くもの | 置かないもの |
| --- | --- | --- |
| `CLAUDE.md` / `AGENTS.md` | 製品境界、権限、安全、完了コマンド | 固定手順、詳細なコード規則、Skill 一覧の再掲 |
| Harness / lint / test / CI | 同じ入力に同じ結果を返す低誤検知の検査 | 設計の好み、開発順序、曖昧な品質判断 |
| Hook | 秘密情報、破壊操作など実行前に止める必要がある安全境界 | reminder、Plan 強制、編集ごとの formatter、CI の重複実行 |
| path-scoped Rule | そのパスでのみ必要な安定した契約 | 全テストへの言語、TDD、No Mock の一律指定 |
| Skill | 反復価値のある任意ワークフロー | 着手・完了の必須入口 |
| Subagent | 独立調査、比較、反証を隔離すると有利な作業 | 単純修正の固定 role play |
| ADR | 長期に残る設計判断と移行理由 | 日々の作業ログ |

## 追加前の判断

1. まず候補の指示、hook、Skill を削除した状態で代表タスクを実行する。
2. 失敗を推測せず、再現可能な例として記録する。
3. 既存のテスト、型、lint、CI、UI 比較で完了条件を与えられないか確認する。
4. 同じ失敗が繰り返される場合だけ、最小の steering を追加する。
5. モデル世代または製品構成が変わったら再評価し、不要なら削除する。

## Verification-first autonomy

モデルへ渡す情報は、詳細な手順ではなく次を優先します。

- 達成するタスク。
- 守る安全境界と非目標。
- 完了を判定できるテスト、実行方法、スクリーンショット比較など。
- 外部副作用または不可逆操作の制限。

方法はモデルに選ばせ、詰まった場所を観測してから補助を追加します。Skill や subagent は任意の道具であり、使わなかったこと自体を失敗にしません。

## Hooks policy

`.claude/settings.json` の hook は、危険な shell command を実行前に止める最小構成にします。以下は常設しません。

- `Plan.md` の作成要求。
- SessionStart、Stop、PreCompact の reminder 注入。
- Write / Edit ごとの formatter、test-style、quality check。
- 設定ファイル編集の一律ブロック。
- commit 時の full gate 実行。

formatter と品質ゲートは明示コマンドと CI に集約します。設定変更も、それが根本修正なら通常の差分として検証します。

## Harness policy

新しい rule は、次をすべて満たす場合だけ追加します。

- 実際に繰り返した失敗を防ぐ。
- 同じ入力へ決定論的に判定できる。
- 誤検知が低く、修正方法を示せる。
- 検出器自身のテストがある。
- 既存の lint、typecheck、test、CI と重複しない。

eval や rule が飽和したら保持を目的化せず、削除または難しい検証へ更新します。
