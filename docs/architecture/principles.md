# Agent Principle Registry

この文書は、AI エージェントが未知の状況で判断するときに使う原則の正本です。

原則は「何を禁止するか」の列挙ではありません。状況によって最適な行動が変わる課題で、証拠の集め方、探索の進め方、候補案の捨て方、完了の判断方法を定めます。

真偽を機械的に判定できる要求は、この文書ではなく [Enforcement Registry](./enforcement-registry.md) に置き、lint、harness、hook、test、CI で強制します。

## 原則の運用

- 原則には安定した `PRINCIPLE_*` ID を付ける。
- 新しい原則は、未知の状況で複数の合理的な選択肢から判断するために必要な場合だけ追加する。
- 正規表現や AST で確実に判定できる要求は原則へ追加せず、enforcement rule にする。
- 原則を変更・廃止するときは ADR で理由と移行を記録する。
- 原則に対応する機械強制がある場合は Enforcement Registry から参照する。

## Principles

### `PRINCIPLE_EVIDENCE_OVER_CONFIDENCE`

説明の流暢さや確信度ではなく、再現可能な証拠を優先する。

証拠には、失敗するテスト、通過するテスト、型検査、実行ログ、計測値、再現手順、差分、スクリーンショット、反例、デプロイ結果を含む。「動くはず」「標準的」「おそらく問題ない」は証拠として扱わない。

### `PRINCIPLE_INDEPENDENT_SEARCH_BEFORE_CONVERGENCE`

複雑な問題では、初期段階から全エージェントを一つの有力案へ収束させない。

異なる定式化、責務境界、データフロー、失敗仮説、利用者視点を独立に探索する。同じ approach family が増えた場合は、人数を追加するのではなく未探索の系統へ振り向ける。

### `PRINCIPLE_EXPLICIT_GAPS`

候補案に残る不足を、曖昧な TODO や楽観的な文章で隠さない。

不足は、未検証の仮定、必要な証拠、再現できていない条件、依存する外部状態、ブロック理由、再開条件として具体的に記録する。元の課題と同程度に難しい問題へ言い換えただけの案は進捗とみなさない。

### `PRINCIPLE_ADVERSARIAL_AUDIT`

候補案は、生成者とは独立した視点から壊す。

監査は一般的なチェックリストの消化ではなく、候補案固有の仮定と失敗条件を攻撃する。正常系の確認だけでなく、境界値、競合、権限、移行、後方互換性、運用、復旧、アクセシビリティ、コストのうち関連する観点を選ぶ。

### `PRINCIPLE_WORKING_INCREMENT`

完成単位は、観測可能な利用者価値を一気通貫で提供する working increment とする。

scaffolding、型だけ、API だけ、見た目だけ、未接続のコンポーネントだけを完了と呼ばない。対象機能に必要なデータ、境界、振る舞い、UI、テスト、運用上の確認を同じ増分へ含める。

### `PRINCIPLE_MINIMIZE_IRREVERSIBLE_ASSUMPTIONS`

不明点を推測で固定せず、安価に反証できる仮説から検証する。

既存コード、履歴、テスト、設定、ドキュメントから解決できる曖昧さは先に調査する。ユーザー判断が必要な不可逆な選択、外部への副作用、秘密情報、破壊的操作だけを確認対象にする。

### `PRINCIPLE_FAIL_LOUDLY_AT_BOUNDARIES`

外部入力、永続化、認証、ネットワーク、ファイル、プロセスの境界では、不整合を正常値へ変換して隠さない。

呼び出し側が中断、再試行、復旧、通知を判断できるエラーとして伝播させる。空配列、偽の成功、固定スタブへの暗黙フォールバックで障害を握り潰さない。

### `PRINCIPLE_SIMPLE_AFTER_EXPLORATION`

シンプルさは、最初に動いた案をそのまま採用することではない。

複数案の責務、依存方向、失敗モード、変更容易性を比較した結果として、最小の概念数と明確な境界を持つ構造を選ぶ。抽象化そのものを目的にせず、同じ変更理由を持つものをまとめ、異なる変更理由を分離する。

### `PRINCIPLE_COMPLETION_REQUIRES_AUDIT`

実装が終わったことと、タスクが完了したことを分ける。

受け入れ条件、残存 gap、adversarial audit、機械ゲート、回帰、外部副作用を確認してから完了とする。未実行の検証がある場合は、その理由と影響範囲を明示し、検証済みであるかのように報告しない。

## Principle と rule の境界

次の問いで配置先を決める。

1. 同じ入力に対して常に同じ真偽を返せるか。
2. 誤検知と見逃しを許容範囲に抑えた検出器を書けるか。
3. 実行前または CI で自動的に止める価値があるか。

すべて満たす場合は enforcement rule にする。満たさず、文脈に応じた比較や証拠評価が必要な場合は principle または review checklist にする。
